# Grounding 规则 — 不编造

README 必须忠实描述实际脚本。这些规则把"不编造"变成可操作条款。

## 规则 1 — 先读再写

动笔前必读：
- `input_schema.json` — 字段名、类型、editor、required、default、enum
- `output_schema.json` — 每个输出列
- `main.py` / `index.js` — 爬取逻辑、硬性上限、增强开关、并发配置
- 已有的部分 README（若有）——只取可验证事实，丢弃无法从代码确认的声明

任何文件缺失或不可读 → 停下并说明，不要凭假设写。

## 规则 2 — 字段名忠实

README 里每个字段名（输入或输出）必须与 schema JSON 逐字一致。大小写敏感。schema 里是 `place_categories`，README 里就必须是 `place_categories`，不能写成 `placeCategories` 或 `Place Categories`。

正文里可用反引号包裹 `place_categories`；JSON 示例里用精确键名。

## 规则 3 — 能力 claim 须引代码

任何"每个 URL 最多 300 条""突破 120 条上限"之类 claim，必须能追到脚本某行或平台文档。脚本没设上限就别编一个。平台硬性上限若有文档依据，引用文档并照抄数字。

不确定就诚实模糊："支持大量类别"，而不是编造"支持最多 100 个类别"——除非脚本或文档真说了 100。

## 规则 4 — 链接：真实或没有

**允许**的链接：
- 平台官方 URL（SKILL.md Sources 里列出的）
- 脚本真实封装的官方上游 API，且链接为稳定官方页（如 Google Places API 文档、Google 服务条款页）
- 仓库内资产（`![view](assets/view.png)`）
- 仓库内锚点（相对 `#section`）

**禁止**：
- 编造的 `https://example.org/some-page`（未验证可解析）
- demo/playground URL（除非仓库真部署了一个且你知道地址）
- issue tracker 链接（除非仓库开了 issue 且你知道 URL）
- OSS 图片 URL（除非是真实存在的 CoreClaw 资产路径）

要占位就别加链接。裸描述好过坏 URL。

## 规则 5 — 输入示例完整可跑

输入示例是用户能直接粘贴到运行输入并获得成功运行的完整 JSON 对象。须含：
- 所有必填字段，带真实值
- 选填字段在需要展示格式时给出
- 精确嵌套（顶层 vs 在 `input` 下 vs 在 `parameters.custom` 下——匹配平台真实运行形态）

平台 v2 运行接口：`POST /api/v2/workers/{workerId}/runs`，scraper 输入放在 `input.parameters.custom`。README 的"输入示例"展示给用户看的是 `input.parameters.custom` 的内容（或等价的 schema 视图），要标注清楚层级。

绝不显示残缺片段如 `{"keyword": "pizza"}`（若脚本还要求 `base_location`）。两者都要给。数组字段给 2-3 个元素，格式无歧义。

## 规则 6 — 输出示例真实

输出 JSON 示例必须：
- 是数组（平台返回结果行为数组）
- 含 `output_schema.json` 的每个列作为键
- 用真实值：保留域名（`example.com`、`example-dental.test`）、占位电话（`+1 512-555-0101`）、合理数字（`review_count: 842`，不要 `999999`）
- 诚实展示可空字段（`email_2: ""`、`email_2_status: ""`）——别裁掉，它们教会用户预期什么

**有真实输出时优先用真实数据**。若用户提供了真实采集输出（如导出的结果 JSON），「完整 JSON 记录」必须基于它构造——真实字段名、真实嵌套结构、真实类型（哪怕是 `""` / `null` / `0` 这类空值也照抄，不要硬改成占位值）。只有以下情况才虚构：
- 真实输出里某字段恒为空（如 `commentsDatasetUrl` 一直是 `""`），但样例需要展示该字段"非空时长什么样"——可填一个保留域名的合理占位值，并在样例后说明真实运行中常见为空。
- 真实输出里某结构一直缺失（如 `effectStickers` 一直是 `[]`），但 schema 里定义了结构——可基于 schema 的 `items`/`fields` 构造一个合理示例。
- 资源链接（图片/视频/音频 URL）过长时，可保留域名与路径结构、用 `...` 缩略中间段，但必须标注"链接为便于阅读做了缩短"。

**字段结构以真实输出为准，不以 schema 推测**。schema 只给字段名和顶层类型，真实输出里的嵌套子字段（如 `authorMeta` 内部、`musicMeta` 内部、`videoMeta.subtitleLinks` 数组形态）只有看真实输出才知道。有真实输出就用真实嵌套，别凭 schema 的 `items`/`fields` 编——编出来的子字段名很可能与上游真实返回对不上。

样例后附一段「真实输出里有几点值得留意」，把真实数据里反直觉的点写出来（如某字段大多数为 `true`、某结构空值与零值的切换规则）——这些是只有跑过真实采集才知道的洞见，对用户最有价值。

这是 worker README 里被复制最多的块。写错意味着每个下游用户的解析器都会坏。

## 规则 7 — 增强开关与脚本一致

脚本有增强开关（联系信息增强、邮箱验证、评论等）时，逐个文档化：default（开/关）、成本（免费增强 vs 运行时成本）、返回什么。不编脚本没有的开关，也不漏脚本有的开关。

## 规则 8 — 诚实能力范围

该说脚本不能做什么时就说。基于代码说明"不支持历史热门时段""评论每地上限 N 条"。诚实能防 support 工单和差评。

## 规则 9 — 面向使用者，不暴露代码内部

README 的读者是**使用 worker 的客户**，不是读源码的开发者。代码对使用者完全透明，README 不得暴露任何实现细节。

**禁止出现在 README 散文里的**（仅指解释机制的散文，不是字段名）：
- 脚本文件名：`main.py`、`config.py`、`input_schema.json`、`output_schema.json`、`actor_client.py`、`sdk.py`、`counter.py`、`requirements.txt`
- 内部变量/配置名：`INPUT_FIELD_MAP`、`DEFAULT_RUN_INPUT`、`ACTOR_ID`、`ACTOR_NAME`、`API_KEY`、`PUSH_MODE`、`concurrency.fields`、`run_input`
- 上游实现术语：`Apify`、`Actor`、`dataset`、`defaultDatasetId`、`run`、`poll`、`gRPC`、`SDK`、"远端 Actor"、"启动 Actor"、"轮询状态"、"读取 dataset"、"映射字段名"
- 任何"worker 合并 X 与 Y""映射 A 到 B""推断列"之类的内部流程描述

**允许保留的**（这些是用户真正看到的东西）：
- 输入参数名（`profiles`、`max_results`、`profileSorting` 等）——用户在表单/JSON 里要填
- 输出字段名（`authorMeta`、`playCount`、`commentsDatasetUrl` 等）——用户在结果表/JSON 里会看到
- 用户可感知的行为与上限（"每个主页最多约 400–500 条""`popular` 返回更少"）

**改写原则**：把"worker 通过 `INPUT_FIELD_MAP` 把 `max_results` 映射到远端 Actor 的 `resultsPerPage`"改写成"每个主页最多采集多少条视频"。把"worker 读取远端 Actor 的默认 dataset，按 `output_schema.json` 推断输出列"改写成"每行一条视频，推入结果表"。讲**做什么、产出什么、有什么限制**，不讲**内部怎么实现**。

判定标准：使用者客户读 README 时，不应出现任何"只有看代码才懂"的词。出现文件名、内部变量名、上游 Actor 术语 → 删掉重写为功能描述。

## 规则 10 — 面向用户的措辞与字段表呈现

README 的每一句散文都是写给普通使用者客户的，不是写给同行开发者的。技术正确但生硬的措辞要改写成用户能直接理解的话。

### 字段表呈现（「提取哪些数据」章节）

用 **emoji 双列表**呈现输出字段，**不列类型、不列裸字段名**：

- **不写类型列**（`object`/`array`/`integer` 等）。普通用户不关心字段类型，类型信息只在「字段详解」按需展开。
- **不写裸字段名**。把字段语义翻译成用户能懂的一句话：`diggCount` → "❤️ 点赞数"；相关字段归并成一句：`createTime`+`createTimeISO` → "📅 发布时间（Unix 时间戳与 ISO 8601 两种格式）"。
- **emoji 前置**，每格一个，做视觉锚点；两列宽度大致均衡；奇数条目时最后一行只填一格，不要留半空行。

### 散文措辞

- **不用"给人看的链接""人读的格式"这类直白到突兀的说法**。改写成用户视角的自然表达："`webVideoUrl` 是可在浏览器打开、跳转到 TikTok 观看该视频的链接"。
- **不堆技术术语解释用途**。"`createTime`（Unix 秒）和 `createTimeISO`（ISO 8601）用于时间序列分析"对普通用户太难懂——改写"用两种格式记录发布时间，一种方便程序处理，一种方便人读，可按发布时间排序或梳理发布节奏"。先说**用户能做什么**，再说**为什么有两个格式**。
- **判断标准**：一个不懂技术的运营/市场人员读到这句，能立刻明白这字段对他有什么用吗？不能就改写。

### 语气基调：通俗与专业并重

README 的语气要**让普通用户看得懂，同时保留专业产品的质感**——既不俯就、也不端着。两条线同时拉：

- **避开通俗到突兀的口语**：
  - ❌ "给人看的链接""人读的格式""主要杠杆是""不用走……那一套""拿到……数据"
  - ✅ "浏览器可打开的链接""两种格式记录发布时间""最直接的手段""无需走……流程""获取……数据"
  - 通则：把口语化的动宾短句换成略正式的同义表达，但不要变成公文腔。"拿到"→"获取"，"拉到"→"拉取/采集"，"跑的是"→"运行的是"，"那一套"→"流程"。
- **避开技术堆砌到生硬的术语**：
  - ❌ 把字段名 + 类型 + 编码格式一股脑塞进一句用途说明（"用于时间序列分析""对象/数组/integer"出现在数据卖点表里）
  - ✅ 先用用户能懂的一句话讲字段**做什么**，字段名用反引号带出即可，类型/编码格式留到「字段详解」按需展开。
- **用规范的产品术语**：采集（不写"抓"/"扒"）、导出（不写"搞出来"）、写入结果表（不写"塞进表里"）、创作者（不写"博主"/"up 主"，除非该平台惯用）、互动指标（不写"数据"含糊带过）。
- **判断标准**：读完一段，像一个专业但好读的产品文档，而不是博客随笔或 API 注释。具体校验——
  1. 不懂技术的运营读到能立刻明白这字段/参数对他有什么用吗？
  2. 懂技术的同行读到会觉得用词准确、不像机翻或口水话吗？
  3. 两条都过才定稿。

## Grounding sheet 模板

动笔前填这张（内联笔记，非交付物）：

```
爬取逻辑: <打哪个源、查询形态、单次请求上限、平台硬性上限>
输入字段:
  - name: keyword, type: string, editor: text, required: 是, default: "", enum: []
  - name: base_location, type: string, ...
  - name: place_categories, type: array, ...
输出字段: <每个 output_schema 列 + 类型>
增强开关:
  - name: <开关>, default: on, cost: 免费/运行时, returns: <字段>
并发: fields=[], remove_fields=[], limits=[], legacy_b=
硬性上限: <如每区域 120 条、每 URL 300 条> — 来源: <代码行或文档>
```

README 每个 claim 都应能追到这张表某行。
